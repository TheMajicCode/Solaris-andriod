# Solaris Android: identity continuity, delegated LUCA, and GPS implementation plan

The shared identity contract at the end supplies the common operation and verification rules; platform-specific summaries do not define a competing protocol. Its proposed signing profile must be frozen jointly before implementation.


Date: 12 September 2026. Status: proposed implementation sequence; no APK, app data, source checkout, repository, or device was modified for this assessment.

## Decision

Continue the latest Solaris Sovereign Edge candidate. Add a portable identity authority subsystem to its existing native boundaries after fixing the text-model and voice preparation failures. Keep the current local vault and daily experience authoritative on the phone. Preserve the private permanent Solaris ID; introduce a replaceable Keet-style controller, scoped device and agent permissions, and an optional proved Nostr binding. GPS uses these permissions and signed evidence; RGB is a later optional asset adapter.

The owner is the principal. LUCA is a delegated agent, never the identity root. Losing or disabling QVAC, Nostr, a web account connection, a relay, Keet/Pear transport, or an RGB wallet must not prevent access to the identity record and core health data.

## 2. Architectural contract

| Layer | Android responsibility | Required property |
|---|---|---|
| Permanent private Solaris ID | Preserve existing local identity and confirmed web-subject association | Not recomputed from a key, npub, email, mnemonic, device, wallet, or DID |
| Owner controller | Versioned Keet-style root attestation adapter; sealed recovery material | Rotatable through an explicit continuity event; optional library implementation, portable verification |
| Device authority | Unique device keys, signed enrollment, permissions, expiry, status | Root attestation establishes membership; application policy establishes allowed actions |
| Nostr binding | Optional possession proof and signer integration | Independent secp256k1 key; private cross-binding unless the owner publishes a chosen public claim |
| Local vault | Existing encrypted state, history, attachments, export and restore | No forced re-encryption or format replacement merely to add identity metadata |
| LUCA authority | Existing local-context and local-authority checks extended with typed capabilities | Data scope, purpose, expiry, destination and budget independently enforced outside model output |
| Sync adapter | Later encrypted own-device synthetic log experiment | Removable; no access dependency for ordinary local use |
| GPS | Deterministic policy evaluation and signed evidence/receipts | One bounded allocation per root ValueEpisode; no payment during replay/projection |
| RGB/wallet | Separate keys, state, signing and restore adapter | No identity seed reuse; no wallet failure that locks health records |

### Permanent ID and local/web reconciliation

An existing APK identity and an existing authenticated web account may not yet share a proven identifier. Treat both as evidence-bearing records until explicitly linked. Never merge because email, display name, or npub happens to match. Never replace the local vault identity with a fresh server response.

A link operation must prove existing local control and authenticated web-account control, show the proposed association, carry a single-use challenge, and retain a signed alias/continuity record. If two established Solaris subjects exist, require the documented account-reconciliation flow; a device link is not an account merge. If no web account is present, local identity continues normally and web registration remains optional.

The controller public key belongs to a controller-history entry underneath the permanent ID. A replacement root changes that entry, not the person's identifier. Prefer a normal owner-approved old-to-new handover while the old key is trusted. If the old key is compromised, use the pre-established recovery authority and record its distinct trust basis; a signature from a compromised key alone cannot resolve the dispute.

### Recovery is more than a mnemonic

The Keet derivation parameters, derivation/library version, controller history, device status, local records, attachment bytes, and approved binding receipts must all be recoverable. A deterministic mnemonic can restore a root key; it cannot rediscover every encrypted record or the latest revocation state by itself.

Keep owner-control recovery separate from vault-data recovery and wallet-state recovery. Recovering account control must not silently reveal old health-data keys to guardians. Restoring a snapshot must reconcile controller/device versions before issuing new online authority. Offline access to already-held records remains possible with a visible freshness status; scarce payouts and new remote actions wait for required fresh authority.

## 3. Shared protocol records and verification rules

Reuse one versioned contract with the web plan; do not invent separate Android semantics. Names below describe proposed records, not existing implementation.

| Record | Minimum content |
|---|---|
| `IdentityContinuity` | Private subject reference, sequence, previous digest, controller algorithm/key/derivation profile, operation, authorizing proof, recovery basis when used |
| `DeviceAttestation` | Controller reference, device key, device-purpose label, enrollment proof, allowed enrollment operation, created time |
| `DeviceAuthorization` | Device key, scopes, audiences, expiry, authority version, status, issuer, signature |
| `IdentityBindingIntent` | Discriminated operation, private subject reference, relevant candidate key/algorithm only, nonce, audience, expiry and prior continuity digest; Nostr is optional |
| `CapabilityGrant` | Human principal, agent key, allowed operations and data categories, destination limits, budget/asset, expiry, revocation reference, issuer proof |
| `SignedEvent` | Type, schema version, random event ID, author, signed payload digest, provenance, timestamps with stated semantics, authority reference, signature |
| `ValueEpisode` | Root economic event, policy snapshot, evidence references, eligible-value basis, asset precision, finite allocations, approval state |
| `OutboxAction` | Idempotency key, approved manifest digest, current authority prerequisites, destination, amount, attempt state and settlement proof |
| `RecoveryManifest` | Format versions, crypto/derivation profile, expected collections/attachment digests, independently verifiable restore checks |

Canonicalization must be explicitly versioned and deterministic. Reject duplicate JSON keys, unknown critical fields, oversized payloads, invalid algorithm identifiers and malformed encodings. Distinguish bytes from display encodings. Sign an application-domain prefix and the exact canonical intent; do not authorize one operation with proof intended for another. Provide shared positive and negative vectors for Node, Android/native, and the optional Bare verifier. Do not hand-roll crypto primitives.

For a Nostr binding, the owner controller/authorized device proves authority for that exact binding operation, and the Nostr signer proves possession over the same intent digest. The server requires a current authenticated account with step-up appropriate to a new external binding. A valid npub string or an unsigned pasted public key is not proof. Reject expired or replayed intents, cross-account substitution, wrong audience, altered operation and cross-environment replay. Nostr proofs do not turn the Ed25519 device key into a Nostr signing key.

Keet source currently verifies an Ed25519 attestation chain and can return both identity and device public keys. It permits device-to-device chain extension, so Solaris must explicitly reject unauthorized subdelegation, even when the library accepts the proof. Its epoch check does not supply a complete device-revocation registry. Pin the actual implementation: current source uses `deriveSeed`, `attestDevice` and `expectedIdentity`, while some README examples differ. [Keet implementation](https://github.com/holepunchto/keet-identity-key/blob/main/index.js).

Membership attestations do not provide device-specific revocation, arbitrary JSON scope enforcement, proof of humanity, clinician qualification, global uniqueness, or trusted time. Solaris must supply scoped policy and issuer validation. A native device-unlock prompt establishes local credential use; it does not independently establish all of these claims either.

## 4. Build sequence and acceptance gates

### A0 — Recover and record the actual candidate

1. Locate the newest D4 source checkpoint, latest complete source/evidence package, and latest packaged APK. Read archive entry paths before extracting to a new isolated directory; reject path traversal/symlink escapes. Inspect materialized files as untrusted project input.
2. Read `AGENTS.md` and referenced governance, node authorization, current-state, release-ledger, architecture, and current Android contracts/handoffs. Reconcile stale instructions with live evidence and this user request.
3. Record actual working directory, branch, HEAD, dirty changes, source-manifest digest, remotes, dependency-lock digests, package/version, signer fingerprint, model-manifest digest and generated-source correspondence. Record source changes present only in a dirty tree. Do not reset, overwrite, or infer native source from web HEAD.
4. Inspect D4 work against D3; determine whether download/voice repairs already exist, are partial, or were never packaged. Preserve that work and identify only the remaining delta.
5. Create a checkpoint before expensive builds. If source remains inaccessible, finish schemas/vectors and a precise blocker report; do not reconstruct a replacement app from an old release.

Acceptance: provenance report identifies exactly which files will be edited and which APK they correspond to, or states the specific correspondence gap without inventing it.

### A1 — Fix the existing text and voice preparation path

This is the first APK workstream. Identity contract work can proceed in parallel with source-independent synthetic fixtures; no new native identity or P2P dependencies should complicate diagnosis of the current failures.

For text AI, trace one request from UI to native downloader, persisted transfer, file publication, runtime service start, model loading, and actual reply. Record redacted stage and reason codes. Separate download, verification, loading, ready-for-inference and first-token states. A completed transfer must never imply working inference.

Reconcile a saved verified file before scheduling anything. Reuse valid staged data; quarantine only demonstrably corrupt data under a retained diagnostic record. Avoid an unconditional delete/redownload loop. Persist a single transfer owner and attach each screen to it. Leaving a questionnaire, locking, or restarting the UI must not create a second download or reset unrelated form state. Respect mobile-data choices, actual free-space headroom, and Android-owned background behavior. Preserve the lazy runtime boundary so passive polling cannot start a native engine.

Android DownloadManager is a background HTTP service that manages retries through connection changes and reboots; app code still owns lifecycle reconciliation and correct status interpretation. It has no public general-purpose pause/resume operation. Do not label cancel/remove as pause. [Android DownloadManager](https://developer.android.com/reference/android/app/DownloadManager).

For voice, first identify the actual provider: current documents describe Android on-device speech, not a second QVAC model download. Check on-device recognizer availability and language support. Android adds on-device recognition in API 31, model-support download in API 33, and listener-based download callbacks in API 34. A scheduled callback promises no subsequent listener progress: recheck support after returning. Respect API/provider differences; an unavailable provider must produce an understandable state while typing remains available. No silent remote recognition fallback. Do not invent an exact byte count when Android does not provide one. [Android SpeechRecognizer](https://developer.android.com/reference/android/speech/SpeechRecognizer).

If a supported offline recognizer cannot be supplied on the target phone, document that verified limitation and propose a separately budgeted optional local voice adapter. Do not add a large Whisper/QVAC/native stack merely to make a button look active.

Acceptance:

- Existing model and records survive the normal update path.
- One permitted transfer, exact manifest verification, model load and a real synthetic reply are demonstrated separately.
- Already verified assets are reused after app restart; wrong hash, unavailable network, insufficient space and process death produce honest recoverable states.
- Offline text inference is explicitly tested on the actual candidate with airplane mode and Wi-Fi off.
- English/Spanish dictation produces a reviewable transcript on supported device/provider combinations; missing support, denied microphone access and scheduled downloads are accurate states.
- Stop, lock, navigation and stale replies never save or display abandoned private output.
- Current Solaris Method progression including Spiritual to Bioelectrical, persisted questionnaire drafts, single-tap actions, scrolling, measured zero/missing values and correction history remain intact.

Physical checks are a distinct evidence gate. Host screenshots, mocked callbacks, and a successful build do not establish phone acceptance.

### A2 — Add identity contracts and a native signer boundary

1. Inventory the current local owner key, identity format, vault encryption key, recovery material, Android Keystore wrapping and any npub binding. Decide what can be retained directly. Never replace keys just because a new library uses a different format.
2. Implement shared records, canonicalization and independent verifiers first. Include synthetic fixtures for a device proof, root/controller rotation and a Nostr binding intent; align them with the web package contract.
3. Add a narrow `IdentitySigner` interface: public identity description, enroll device, prove scoped challenge, sign permitted event, rotate by authorized continuity operation, export encrypted recovery descriptor. No arbitrary private-key getter or unrestricted sign-any-bytes bridge.
4. Keep owner root material out of WebView, the QVAC/Bare inference worker, JS logs and AI context. Use a dedicated signer service/module with explicit request validation and foreground approval for controller changes. A separate Bare isolate inside the inference process does not satisfy this separation.
5. Test exact Ed25519 support on the intended Android signer path. Android hardware-backed support must be measured, not assumed. If the seed is software-managed but encrypted with a hardware-backed wrapping key, describe that accurately and minimize its lifetime in signer memory. [Android Keystore](https://developer.android.com/privacy-and-security/keystore).
6. Integrate Keet-style derivation as a pinned adapter only after deterministic cross-runtime vectors, cold restart, package compatibility and native-memory tests pass. Preserve exact derivation metadata for recovery. Prefer a Kotlin/native wrapper or isolated minimal signer service over injecting the root into the existing AI worker.
7. First demonstration uses synthetic data: create test controller, enroll two independent devices, attest a payload, verify on another runtime, recover identical controller with identical derivation profile, deny an altered payload, then rotate the controller without changing the synthetic subject ID.

Acceptance: another verifier accepts valid proofs and rejects tampering; no model context can access signing secrets; root rotation preserves subject continuity; unavailable Keet adapter does not block the existing vault. Hardware protection claims identify exactly which key/operation is protected.

### A3 — Private Nostr binding, web account linking, and useful device UX

Implement the shared dual-possession challenge flow. Keep the current npub login/binding if it exists; migrate it explicitly to a proved binding only when the corresponding possession checks succeed. Store pending/unverified/revoked states distinctly. Use external Android/Nostr signing where supported; assess Amber/NIP-55 as an adapter without requiring it for vault access. A signed binding receipt must be exportable and independently verifiable without exposing the private permanent ID on public relays.

Present a compact owner settings surface with `This device`, `Linked devices`, `Nostr connection`, `Recovery`, and `LUCA permissions`. Keep the daily UI familiar. Device names are labels; the proof binds actual keys. If using NIP-46, obtain the user signing key via `get_public_key`; do not bind the client/transport key. NIP-46 signing permissions do not implement Solaris health-data scopes or wallet budgets. [NIP-46](https://github.com/nostr-protocol/nips/blob/master/46.md). Link a second device using an expiring invitation and mutually authenticated exchange, with a human-checkable confirmation. Invitation consumption is one-time; network completion alone must not authorize enrollment.

Everyday login/biometric unlock must not ask for a 24-word phrase. Existing users should reach their current dashboard and see optional identity features only when relevant. Recovery enrollment requires an explicit informed flow but cannot gate access to records the owner already controls.

Acceptance: fresh authorized links succeed; replay, wrong audience/account/key, canceled approval and expired invitations fail. Revoking a device denies subsequent new authority where fresh state is available; existing downloaded plaintext cannot be retroactively recalled. The user can unlink Nostr and retain their identity and vault.

### A4 — Give LUCA bounded authority and generate GPS shadow evidence

Extend existing `local-context` and `local-authority` modules rather than adding a second consent model. Create a short-lived agent key/identity with capabilities referencing approved source categories and exact tools. Default spend allowance is zero. Use named operations such as `read_selected_records`, `draft_note`, and `propose_next_step`; booking, sharing and payment remain separate capabilities with explicit destination and approval rules.

Model output is a proposal. A deterministic validator rechecks the live vault session, capability, source access, revocation and operation arguments immediately before any side effect. Root keys and unrestricted wallet signing are unreachable from tools. Lock/revoke/Stop invalidates pending requests and their downstream writes.

Represent a synthetic contribution as signed evidence, then compute a GPS shadow allocation using the same versioned policy package as the web. The existing showcase and payment-pilot profiles must be reconciled explicitly; do not hardcode a permanent 90/10 or 86/4/10 interpretation in Android. Establish eligible value, exclusions, root ValueEpisode, selected policy version and authority. A hash-only receipt is not equivalent to a signed verified receipt, and a signed statement is not automatic proof of real-world truth.

Acceptance: capability revocation during a pending model request prevents the action; disallowed categories remain inaccessible; synthetic GPS output reproduces web vectors exactly; zero funds move; replayed events never create another allocation.

### A5 — Experiment with encrypted own-device replication

Start with one synthetic note between two test devices or phone and laboratory node. Keep existing health storage; add an optional adapter boundary for a separate Corestore/Hypercore namespace. Derive neither discovery topics nor public network identifiers directly from the private permanent ID. Define encryption keys, writer admission, payload schema, resource bounds and backup locations before enabling transport.

Use the root/controller proof to authenticate device membership, then application policy to admit each writer. Signed note authorship proves which accepted key signed bytes; it does not certify clinical truth. P2P confidentiality requires explicit encryption and key distribution. Logs and indexes are distinct: maintain deterministic projections and retain provenance. Corrections append events rather than pretending earlier replicated bytes disappear.

Corestore namespaces are not complete security boundaries; inventory exactly which loaded cores the adapter can replicate and which master/read keys it holds. Hyperswarm transport keys and topic membership are not application authority. [Corestore](https://github.com/holepunchto/corestore), [Hyperswarm](https://github.com/holepunchto/hyperswarm).

Use Autobase only if the experiment truly needs concurrent writers. Its reducer must be deterministic and replay-safe: no tools, GPS payouts, HTTP calls or notifications inside `apply`. Emit immutable candidate intent records; a separate durable outbox processes approved actions with idempotency and current-authority checks. Do not assume arrival order is final order. [Autobase](https://github.com/holepunchto/autobase).

A blind peer can help availability only for data actually replicated and retained there. Blind peering, discovery and NAT traversal do not magically store an offline peer's unread history. Measure what the chosen service can access, retain, correlate, and delete. Keep user-selected backup independent from discovery infrastructure. Treat blind pairing (rendezvous) and blind peering (commissioned encrypted mirrors) as distinct. Never provide a blind mirror with the content read keys. [Blind pairing](https://github.com/holepunchto/blind-pairing), [blind peering](https://github.com/holepunchto/blind-peering).

Acceptance: disconnected local editing, authenticated replication, duplicate and reordered delivery, invalid writer rejection, bounded storage, restore on a fresh synthetic installation, and removal of the sync adapter all work. Signed health records and practitioner collaboration remain later, separate scopes.

### A6 — RGB experiment after identity/recovery/GPS semantics work

Add one replaceable wallet/asset adapter in a separate laboratory build or feature flag. Keep identity and wallet seeds separate. Start with a synthetic clinic-service-credit case and fixed supported RGB schema; verify exact stack lineage, versions and interoperability. Do not mint a general Solaris identity/reputation token, promise automatic GPS enforcement by Bitcoin, or imply that the entire GPS policy suite executes in RGB.

Require restoration of the asset history/consignment and any Lightning state, not only a mnemonic. A phone's replicated health vault and a live Lightning wallet have different concurrency requirements. Enforce one owner of active wallet state; never merge live channel files with general multi-writer sync. Sign approved finite transfers through an independent wallet policy interface and durable outbox.

Acceptance: issue, receive, inspect, redeem/correct where supported, export, restore and interoperate using test assets; prove the core vault still opens with the wallet adapter removed. Real funds and clinic obligations require a separately explicit pilot scope and current rail assurance review.

## 6. Cross-app integration gate

The web and Android implementations must exchange the same synthetic fixture bundle. Required cases: valid device proof; controller rotation; signed Nostr-binding challenge; wrong-account and wrong-origin rejection; device revocation; revoked LUCA capability; GPS one-episode allocation; duplicate/out-of-order event delivery; archived signed receipt verification.

## How the Keet findings change the architecture decision

The strongest fit is a permanent Solaris subject with replaceable, independently verifiable controllers and adapters. Keet adds a practical portable controller/device proof pattern. It does not require Solaris to become Keet, adopt all of Pear, move health records into Nostr, or put identity on a blockchain. The enduring unit is the person/entity's private continuity record; the controller key is one authority over that record.

### Identity, human eligibility and delegated trust

Treat four questions separately: who controls this account, which device/agent may act, which claims an issuer makes about the subject, and whether this subject is eligible for a particular benefit. Generating a new cryptographic root is inexpensive; it cannot prove one unique human or prevent someone obtaining several roots.

Add issuer-scoped `TrustCredential` records only when needed: issuer, pairwise subject reference, claim type, evidence reference, scope/audience, issue/expiry, revocation reference and signature. The relying service selects accepted issuers and evidence thresholds. A clinic can attest a professional relationship or qualification within a defined process; a community can attest participation; a campaign can enforce its own duplicate-claim rule. Those assertions are not universally interchangeable and trust is not automatically transitive.

Keep recovery guardians distinct from credential issuers and record readers. Guardians may have pre-registered authority to recover account control without access to health decryption keys. High-value recovery needs an explicit threshold, conflict procedure, fresh-state checks and limited post-recovery permissions, chosen in the contract. Avoid a single global reputation score or token-weighted identity authority. Claim-specific pseudonyms reduce unnecessary cross-context linkage.

### Local-first and regenerative success criteria

The near-term demonstrable product is: an owner keeps the same private Solaris identity across key/device changes, opens recovered records with the service offline, delegates one bounded LUCA task, and verifies a signed GPS shadow receipt. This can be demonstrated before paid infrastructure, a public token, full P2P replication or production RGB settlement.

Test that product under intermittent connectivity, constrained storage, limited mobile data and midrange-device memory pressure. Measure bytes transferred per successful synchronization, wakeups/background battery drain, time and memory per useful local task, export/restore success, and the proportion of core tasks completed offline. Measure energy for equivalent useful work before claiming local AI, RGB or a specific chain is more energy-efficient. An idle mesh and frequent unnecessary polling can negate local-first gains.

Regenerative GPS rewards require a declared outcome and credible measurement, not only a signed activity log. Keep self-report, attested work, verified contribution and measured health/ecological outcome distinct. Publish the chosen policy's eligible-value basis and beneficiary accounting. AI can accelerate implementation and analysis; it cannot substitute for independent cryptographic review, recovery exercises, incentive-abuse testing or physical-device evidence.

### Shared sequencing across the two products

1. Web W0 establishes current source and deployment boundaries; APK A0/A1 recovers the latest candidate and fixes existing model/voice failures.
2. Jointly freeze one identity protocol and synthetic fixtures. Web W-ID1 can use a minimal local reference signer while APK A1 proceeds; do not force new native dependencies into the reliability release.
3. Connect web W-ID1/W-ID2 with APK A2/A3. Demonstrate private existing-account association, candidate possession, device lifecycle and recovery continuity with the same fixture suite.
4. Connect web W-AUTH1/W-EXPORT1/W-GPS1 with APK A4. Demonstrate scoped LUCA action, independent restore and exactly one GPS allocation in shadow mode.
5. Add one synthetic own-device sync experiment, then one separately recoverable RGB asset experiment. Expansion follows evidence, not a calendar promise.

Use one versioned protocol source of truth. If the applications live in separate repositories, publish or vendor an immutable schema/vector package with a digest and explicit compatibility version; neither team edits its own incompatible copy. Platform adapters own storage, UI and transport. Shared validators own byte-level interpretation and policy inputs. Preserve old proof/receipt verification when introducing new versions.

## Shared identity contract for the web and APK plans

This is a proposed application protocol, not an existing Keet/Nostr standard and not an accepted production contract. Both implementations must publish the same versioned schemas and conformance vectors before linking real accounts.

### Identity and authority

The permanent private Solaris Subject ID identifies the person/entity within Solaris. A replaceable controller-root binding establishes cryptographic control. Root-attested device keys identify devices; separate capability grants authorize actions. LUCA is a separately attributable agent. Nostr is an optional communication binding; wallets remain separate financial authorities. The controller root is not the Subject ID and not LUCA itself.

Existing users keep their Subject ID, vault identifiers, records, foreign keys, Nostr bindings, recovery material, and application-signing continuity. A separately created offline identity can attach to an existing account only through an explicit, authenticated reconciliation transaction. Never merge by matching email, npub, device key, or a self-asserted Subject ID. A controller key cannot claim an existing account merely by signing its identifier.

### Private operation-bound proofs

Define `IdentityBindingIntent` as a discriminated union. Common fields are `format`, `bindingId`, private `subjectId`, `operation`, `audience`, approved `origin`, nonce, `issuedAt`, `expiresAt`, and previous continuity sequence/digest. Each operation admits only its declared candidate fields and exact requested authority. Nostr is optional; controller enrollment must not require a Nostr account or signature.

| Operation | Required authority | Required candidate proof |
|---|---|---|
| `enroll-controller` for an existing account | Current authenticated account, independent recent step-up and explicit enrollment confirmation | Candidate controller-root possession |
| `link-nostr` | Current controller or a device explicitly authorized to manage this binding; account step-up for the web mutation | Candidate Nostr user-key possession |
| `add-device` | Current controller or an explicitly authorized enrollment issuer within its delegation scope | Candidate device-key possession and accepted root-membership proof |
| `rotate-controller` | Current controller or recovery authorization under a policy registered before the incident | New controller-root possession |

Each required proof refers to the same operation transcript. Nostr linking therefore needs both authorized Solaris control and Nostr possession. It cannot establish the initial account association by itself.

A pairing relay carries only an opaque encrypted request. Private identifiers and recovery material must not appear in public Nostr events, URLs, telemetry or QR payloads. A QR code carries a short-lived pairing reference and public ephemeral exchange material. The authenticated pairing transcript binds the issuer identity, candidate device key, both endpoints' ephemeral exchange keys, requested scope, audience, nonce and expiry. Require candidate-device possession and confirmation of the same transcript fingerprint or short authentication string on both endpoints. Encryption or scanning a QR alone is not device authorization. Use a reviewed authenticated exchange implementation rather than inventing one.

The proposed signing profile is JCS UTF-8 over the unsigned transcript, excluding proof objects; prepend exact ASCII bytes `SOLARIS_IDENTITY_INTENT_V1` followed by one LF byte. Hash these framed bytes with SHA-256 and display the digest as lowercase hexadecimal. Times are integer Unix seconds; keys use the algorithm's explicitly declared lowercase-hex public encoding; binary Keet proofs use unpadded base64url; nonce is 32 cryptographically random bytes encoded as unpadded base64url. Monetary minor units are decimal strings, avoiding floating-point allocation arithmetic. Reject duplicate keys, unsupported fields/algorithms, malformed encodings, invalid Unicode, oversized proofs and excessive certificate chains. Use established libraries; do not invent signature algorithms or modify upstream proof formats. [JCS informational RFC](https://www.rfc-editor.org/rfc/rfc8785).

For applicable operations the controller/device produces a Keet-compatible proof over the framed bytes. For `link-nostr`, the independent Nostr signer signs a Nostr event carrying the same digest. Candidate application wrapper: `kind: 30078`, `created_at` equal to transcript `issuedAt`, expected user `pubkey`, exact ordered tags `[["d","solaris:identity-proof:<bindingId>"],["purpose","solaris-link-nostr-v1"]]`, and `content` equal to JCS of `{"format":"solaris-identity-proof/1","intentDigest":"<lowercase SHA-256 hex>"}`. This is Solaris-specific app data, not a new Nostr identity standard or a replacement for relay/HTTP authentication. No relay publication is needed. Each scheme retains its native signing procedure; the Nostr signature signs the NIP-01 event, not raw digest bytes. Verify the complete event, expected root and Nostr user key, current authority and transcript equality. In NIP-46, obtain the user's key through `get_public_key`; do not bind a transport key. [Nostr signing](https://github.com/nostr-protocol/nips/blob/master/01.md), [app-data kinds](https://github.com/nostr-protocol/nips/blob/master/78.md), [remote signer](https://github.com/nostr-protocol/nips/blob/master/46.md).

Before either app implements this candidate profile, one joint contract must freeze its exact schema, algorithm IDs, size limits, clock tolerance, proof container, event wrapper, canonical bytes and expected vectors. Test actual selected NIP-07/46/55 signers. Amend the candidate explicitly if interoperability requires it; never let the two apps silently implement different profiles. Existing raw-challenge Solaris signatures keep a separately versioned compatibility path.

Account enrollment additionally requires a valid existing account session, independent step-up, explicit user confirmation and one-use server challenge. Use the approved challenge TTL; reconcile the current 120-second contract versus five-minute implementation before changing semantics. Consume the nonce and append the binding in one transaction with unique constraints and expected-previous-version checking. A root proof plus an arbitrary copied Subject ID is rejected. Subsequent ownership changes require existing authorized controller approval or the previously registered recovery policy, not possession of an ordinary session alone.

### Lifecycle and recovery

Keep `IdentityContinuity`, `DeviceAttestation`, `DeviceAuthorization`, `CapabilityGrant`, `BindingChange`, `RootRotation`, and `RecoveryPolicy` separate. `DeviceAttestation` retains the upstream proof and format; `DeviceAuthorization` is the Solaris policy record that refers to that proof and supplies current permissions. Define who may add devices, whether they may delegate further, capability attenuation, expiry, revocation, and fresh-state requirements. The Keet proof chain is evidence inside this check; it is not the entire authorization decision. The initial device profile cannot add arbitrary devices or authorize payments by default.

Normal rotation proves control of old and new controllers. Compromise recovery follows a recovery policy registered before the incident; it must not require the stolen key when that would defeat recovery. Manual intervention cannot silently invent a replacement root. If no valid recovery path exists, preserve the data and explain the inability to establish authority. Conflicting successors of one continuity head enter a conflict state; wall-clock ordering or last-write-wins must not select the owner.

Local possession/unlock continues to permit already-authorized local record access during network outages. New consequential operations need suitably fresh revocation and policy state; disconnected peers cannot guarantee knowledge of all new revocations. Reconnection reconciles authority before releasing queued consequential actions. Historical evidence retains its original signer and any later invalidation annotation.

Persist the last accepted continuity sequence and digest and reject regression or a conflicting successor. Verification must distinguish `signature-valid`, `authorized-at-known-checkpoint`, and `currently-authorized`. A clean restored device cannot infer freshness from a valid older signed backup: reconcile an authenticated continuity head through the owner's configured authority/replica sources before consequential actions. Declare the sources' trust and availability requirements. Local replay detection sees locally known events; global duplicate-claim prevention requires reconciliation or an explicit coordination authority.

A 24-word phrase restores a controller root only under the matching derivation profile. The complete recovery bundle also needs the private Subject ID and accepted binding history, recovery policies, encrypted records, encryption-key recovery material, schema versions, integrity manifest, and any necessary log/discovery metadata. Wallet recovery is separate and includes required current asset/channel state. Do not overwrite existing credentials or repurpose an installed wallet/vault seed as the new identity root. New-device pairing should authorize a fresh device key without routinely copying the root secret to every device.

### GPS, replication and actual authority

Preserve `ValueEpisode`, versioned `PolicySnapshot`, signed evidence, finite `AllocationManifest`, and per-output `SettlementReceipt`. One GPS execution per root ValueEpisode; child agent calls do not recursively create new ecosystem charges. Resolve the eligible basis and scoped policy profile before commitments; retain the existing <=10% envelope and recipient-owned pending entitlements. Device proof does not establish professional qualification, unique humanity, true contribution, or payment authority.

Autobase views may reorder/replay. A pure reducer can derive proposed records, never execute network calls, payments, notifications with economic effect, or clinical actions. Use a separate durable outbox with stable event/output identifiers, reservation and transactional deduplication. Recheck current authority, approved policy and destination immediately before execution; query uncertain settlement status before retrying. Do not CRDT-replicate live RGB/Lightning wallet state: those adapters need a single active writer and controlled migration.

Begin synchronization with one encrypted synthetic personal note between two owned devices. Keep clinical writers separately attributable. Patient consent, clinician authorship, approval and correction are separate events; do not require a patient signature on every clinician-authored record or merge conflicting clinical decisions into a final plan automatically. Mirror replication never includes read keys. Export remains usable when any one server, Nostr relay, mirror, model, or wallet adapter is unavailable.

Revoking authorization cannot remove encryption keys or plaintext already held by a device. Excluding a removed device from future records also requires a new encryption-key epoch and, where the pinned storage protocol requires it, new log/room material distributed only to remaining authorized devices. Retain historical decryption and corrections under the relevant retention policy; do not claim to retract copied data. Backups must inventory these key epochs without giving blind mirrors read keys.

### Joint acceptance gate

The web and APK verifiers must accept the same authorized transcript and reject altered content, wrong root, wrong Nostr key, reused nonce, wrong audience/origin, expiry, subject substitution, unauthorized subdelegation and conflicting continuity. The clean-device exercise separately demonstrates root restoration, account binding continuity and encrypted-record restoration. A replayed data reducer produces no extra GPS allocation or external side effect. Tests use synthetic accounts and records; no live user reset or funded-wallet experiment is part of this gate.
