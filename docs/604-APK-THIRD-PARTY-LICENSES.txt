SECTION 9 -- COVERAGE GAPS, NAMED, NOT ASSUMED AWAY

================================================================================

This section exists because a table of license names, or a claim of
completeness, is not itself evidence. The following are the concrete,
specific gaps that remain after this task; none of them is grounds to
withhold this APK, and none is glossed over as resolved:

  1. bare-kit's own precise bundled version could not be established with
     confidence. Strings embedded in libbare-kit.so include a run of
     version-like numbers (1.0.0 through roughly 1.52.1) that read more
     like an embedded changelog than a single definitive build marker.
     Its LICENSE text (Section 1) is version-invariant Apache-2.0, so this
     does not affect the license conclusion, only the version citation.

  2. libbare-kit.so is a large (63,082,800-byte) aggregate binary. This
     task confirmed two additional statically-linked third-party components
     inside it beyond the "bare-kit" JS-level package identity -- BoringSSL
     (Section 2.6) and libuv (Section 3.5) -- via their own embedded
     build-path and runtime-message strings. A full, exhaustive audit of
     every component that may be statically linked into this one binary
     was not performed; further such components may exist and have not
     been ruled out.

  3. Exact Apache Commons Codec version is not established from binary
     evidence -- only its exact resource-file set (127 Beider-Morse rule
     files) confirms its identity. Apache-2.0 applies regardless of the
     exact version.

  4. Exact per-module versions for Hermes, React Native,
     react-native-safe-area-context, Fresco, fbjni, the Kotlin standard
     library, and the individual Expo native modules were not extracted
     from the binary. Where a version was used to select a specific
     upstream tag to fetch from (react-native, fetched at v0.81.4), that
     version is itself an inference from the Expo SDK version recorded in
     app.config (54.0.0) and Expo's own published SDK-to-React-Native
     pairing, not a fact read from this binary's own bytes.

  5. The full JS-only npm dependency graph recorded in this repository's
     own Solaris-Android-Reconstruction/build-inputs/packaged-dependencies.json
     (136 entries) includes roughly 85 packages with no corresponding
     native .so file in this APK (for example: hypercore, hyperdrive,
     hyperswarm, hyperbee, hyperdht, corestore, protomux, noise-handshake,
     streamx, tar-stream, zod). These were not individually license-checked
     in this task, and -- more importantly -- their actual presence and
     reachability inside the compiled Hermes bytecode
     (assets/index.android.bundle) was not independently confirmed one by
     one; packaged-dependencies.json records what was in the workspace's
     dependency tree when the app was built, which is not the same claim
     as "this exact file's compiled bytecode contains this exact package's
     code." This remains open, unresolved scope, distinct from -- and
     narrower than -- the repository's still-open AND-01 dependency/license
     audit, which covers the whole repository, not just this one binary.

  6. No byte-for-byte diff was performed between any native library above
     and its claimed upstream source, except the OkHttp Public Suffix List
     component (Section 5), where it was performed twice with an identical
     result both times.

None of the above changes this task's conclusion: no reciprocal
(GPL/LGPL/AGPL) copyleft applies to this APK's own code once RocksDB's
Apache-2.0 option is elected (Section 7); the one weak, file-level copyleft
component present (MPL-2.0, Section 5) has both its conditions verified met;
and this file, together with docs/604-APK-THIRD-PARTY-NOTICES.md, is the
complete legal-text package for every component this task was actually able
to identify and verify -- not for the JS-only dependency graph named in
gap 5, which is separate, already-disclosed, still-open scope.
